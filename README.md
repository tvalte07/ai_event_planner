# AI Event Planner Agent

A local-first event planning application developed in phases. **Phases 1 through 8 are implemented.** The application includes planning, memory, RAG, agents, MCP, APIs, tests, and container configuration.

## Phase 2 features

- Event name, type, date, location, guest count, budget, start time, preferences, and additional requirements.
- Input validation for required fields, supported event types, date, guest count, and positive budget.
- Illustrative budget allocation across venue, food, decoration, occasion items, activities, and contingency. Integer rounding is distributed so allocations exactly equal the entered total.
- Venue category suggestions loaded from `data/sample_venues.json`, filtered by event type and sample capacity. These are categories and selection questions, not live venue listings.
- Event-type-specific schedule with adjustable start time.
- Catering, decoration, and guest-management suggestions that reflect the provided preferences.
- Streamlit tables and a budget chart.

The planning services in `app/services/event_planner.py` are independent of Streamlit and use deterministic local logic. The plan is not generated by the LLM yet; agent orchestration is reserved for a later phase. Budget values are planning allocations, not vendor quotes. The app does not search for or claim venue availability, real prices, or contact details.

## Phase 3: memory and tools

- `app/memory/database.py` creates the local SQLite tables for event history and profile preferences.
- `app/memory/memory_manager.py` stores planned events, food and decoration preferences, general notes, preferred location, and average budget. The Streamlit form pre-fills saved preferences for the selected local profile.
- The default database is `data/planner_memory.sqlite3` and is ignored by Git. A profile ID separates local records but is only a label, not authentication or encryption.
- `app/tools/` contains standalone tools for budget calculation, budget validation, invitation-count estimation, event schedule generation, literal text-document search, and event summaries.
- The text search tool scans local `.txt` and `.md` files only. It does not read PDFs or provide semantic retrieval; document extraction and RAG are planned for Phase 4.
- Tool functions use ordinary Python types and do not depend on LangChain. This keeps the current phase light; framework wrappers can be added during agent integration.

## Phase 4: document RAG

- Upload PDF or TXT files in the Streamlit document section. PDF text is extracted with pypdf, split into overlapping chunks, embedded with Ollama `nomic-embed-text:latest`, and stored in a persistent local Chroma collection.
- Ask a question to retrieve the closest chunks and draft an answer using only those excerpts. The prompt instructs the local Qwen model to say when the excerpts do not contain an answer and to cite source filenames.
- Ready-to-upload demo PDFs are in `data/uploads/`; suggested questions and a grounding check are in `data/sample_rag_questions.md`.
- Chroma data is stored under `data/chroma/` and is local to this machine. Re-indexing the same file creates new chunks; this MVP does not deduplicate or delete prior versions.
- RAG requires Ollama, `nomic-embed-text:latest`, and the Python dependencies in `requirements.txt`. Event planning continues to work if these optional imports are not installed, but upload/search will show an error until setup is complete.

## Phase 5: sequential agent workflow

- `app/agents/state.py` defines the shared TypedDict state.
- `app/agents/nodes.py` contains validation, budget, venue, schedule, and final event-manager nodes. The first four perform bounded deterministic work; the final manager calls the configured local Ollama model once to consolidate the results.
- `app/graph/workflow.py` wires the nodes sequentially with a validation route that stops on invalid event details.
- The planner UI exposes **Generate consolidated AI plan** after creating the deterministic starter plan.
- Install the LangGraph and LangChain Ollama dependencies from `requirements.txt`. Tests mock model output; live generation requires Ollama and `qwen3:4b`.

## Phase 1 architecture and local model

- `app/config.py` reads Ollama settings from environment variables and supplies local defaults.
- `app/llm/ollama_client.py` calls the local Ollama HTTP API using Python's standard library.
- The UI has a collapsible Ollama setup check; event plan generation does not require Ollama to be running.
- `frontend/streamlit_app.py` is an alternate Streamlit entry point.

The optional LLM request is sequential and uses a 4,096-token context limit and short output limit for CPU execution. No paid API or API key is used.

## Requirements

- Python 3.12.7 is the verified target environment for this project.
- Ollama at `http://localhost:11434` with `qwen3:4b` for grounded answers and `nomic-embed-text:latest` for RAG.

Python 3.12.7 is the target used for project verification. LangChain's Ollama integration is not used by the RAG implementation; the project calls Ollama's local HTTP API directly to keep the dependency set small.

## Setup

In PowerShell, from the project root:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements-dev.txt
Copy-Item .env.example .env
```

The app reads `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, and `OLLAMA_TIMEOUT_SECONDS` from the process environment. Phase 1 intentionally avoids an extra dotenv dependency, so set those environment variables in your shell if you want to override the defaults. To use the optional Ollama check, start Ollama and pull the model:

```powershell
ollama pull qwen3:4b
```

## Run

```powershell
streamlit run app/main.py
```

Run the API in a second terminal with `python -m uvicorn app.api.main:app --reload`. Swagger docs are at `http://127.0.0.1:8000/docs`.

Fill in the form and select **Create event plan**. The resulting plan shows the budget breakdown, venue categories to explore, catering and decoration suggestions, schedule, and guest-management checklist.

## Verify

```powershell
python -m compileall app frontend tests
python -m pytest -q
python -m streamlit --version
```

The tests cover budget arithmetic and validation, event input validation, schedule timing, local sample venue filtering, preference handling, SQLite persistence and profile isolation, invitation estimates, text search, and summaries. They do not require Ollama. Local venue categories and budget shares remain illustrative until a later phase integrates verified external data sources.

## Project status

- **Phase 1:** project setup, Streamlit shell, local Ollama configuration and connectivity check.
- **Phase 2:** event form, budget calculation, sample venue categories, schedule, and starter plan.
- **Phase 3:** SQLite event memory and reusable tools.
- **Phase 4:** PDF/TXT ingestion, chunking, Ollama embeddings, Chroma storage, retrieval, and grounded answers.
- **Phase 5:** typed shared state, sequential LangGraph nodes, and final local-model consolidation.
- **Phase 6:** FastMCP server exposes budget, schedule, guest-list, event-detail, and document-search tools. `app/mcp/client.py` demonstrates MCP tool discovery and invocation using a real in-memory MCP client transport. Run the server with `python -m app.mcp.server`; run the discovery demo with `python -m app.mcp.client`.
- **Phase 7:** FastAPI REST API is in `app/api/`, with interactive Swagger docs at `/docs`. Run it with `python -m uvicorn app.api.main:app --reload`.
- **Phase 8:** pytest coverage, Dockerfile, Compose configuration, and deployment instructions.

## Docker

Start host Ollama and pull `qwen3:4b` and `nomic-embed-text:latest`, then run:

```powershell
docker compose up --build
```

Streamlit is available at `http://localhost:8502` (host port 8501 was already occupied); API docs are at `http://localhost:8000/docs`. The project `data/` directory is bind-mounted so SQLite, Chroma, and sample files persist and remain visible. Compose connects containers to host Ollama through `host.docker.internal`.
